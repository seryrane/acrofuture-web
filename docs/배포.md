# 배포 — GitHub Pages

`main` 에 밀면 GitHub Actions 가 굽고 Pages 가 낸다. **사람이 빌드해서 올리지 않는다.**
빌드 산출물(`site/out`)을 저장소에 넣지 않는 이유가 이것이다 — 누가 한 번 빌드를 잊으면
"고쳤는데 옛 화면이 나온다"가 되고, 그건 보는 사람에게 사이트가 고장 난 것으로 보인다.

```
로컬에서 고침 ──▶ git push origin main
                      │
                      ▼
        .github/workflows/deploy.yml
        npm ci ──▶ npm run build ──▶ site/out ──▶ Pages
                   (output:'export')
                      │
                      ▼
                acrofuture.com
```

## 한눈에

| 항목 | 값 |
|---|---|
| 저장소 | `seryrane/acrofuture-web` (공개) |
| 배포 방식 | GitHub Actions (Pages source = **GitHub Actions**, 브랜치 배포 아님) |
| 도메인 | `acrofuture.com` — `site/public/CNAME` 에 박혀 있다 |
| 빌드 | `site/` 에서 `npm ci && npm run build` → `site/out` |
| 배포 시간 | 대략 1~2분 |

상태 보기: `gh run list -L 5` · 실패 로그: `gh run view --log-failed`

## ⚠ 도메인은 DNS 문제가 아니었다 — **다른 계정이 선점하고 있다** (2026-08-13 실측)

지금 `acrofuture.com` 은 **이미 GitHub Pages 위에 있다.** 다만 우리 계정이 아니다.

```
가비아 DNS  acrofuture.com ──▶ 185.199.108/109.153 ──┐
                                                     │  GitHub 은 Host 헤더로 저장소를 고른다
                              acrofuture.com 을 등록해 둔 저장소 = snake0207 계정
                                                     ▲
      seryrane/acrofuture-web ──✗───────────────────┘  "already taken" (HTTP 400)
```

그래서 **가비아에서 DNS 만 바꾸면 아무 일도 일어나지 않는다.** 어차피 같은 GitHub IP 로 가고,
그 안에서 누구 사이트를 낼지는 도메인을 등록한 저장소가 정하기 때문이다.
`snake0207` 계정에는 접근할 수 없다(외부 제작). 그래서 **소유 증명으로 회수**한다.

### 1단계 — 도메인 소유 증명 (선점 해제)

1. https://github.com/settings/pages → **Add a domain** → `acrofuture.com`
2. GitHub 이 TXT 레코드 이름·값을 준다 (`_github-pages-challenge-seryrane`)
3. 가비아 DNS 에 그 TXT 를 넣는다
4. GitHub 에서 **Verify** — 초록이 되면 이 계정이 도메인을 독점하고 선점이 풀린다

### 2단계 — 저장소에 도메인 등록

```bash
gh api --method PUT /repos/seryrane/acrofuture-web/pages -f cname=acrofuture.com -f build_type=workflow
```

### 3단계 — 가비아 DNS 정리

⚠ **바꾸기 전에 지금 레코드를 적어 둔다.** 되돌릴 때 그게 없으면 못 돌아간다.
2026-08-13 실측값은 아래 "바꾸기 전 상태"에 남겨 뒀다.

| 호스트 | 타입 | 값 | 비고 |
|---|---|---|---|
| `@` | A | `185.199.108.153` | 유지 |
| `@` | A | `185.199.109.153` | 유지 |
| `@` | A | `185.199.110.153` | **추가** (빠져 있었다) |
| `@` | A | `185.199.111.153` | **추가** (빠져 있었다) |
| `@` | A | ~~`211.236.39.251`~~ | **삭제** ⚠ 아래 참고 |
| `www` | CNAME | `seryrane.github.io` | 기존 `snake0207.github.io` 대체 |
| `www` | A | ~~3개~~ | **삭제** — CNAME 과 A 는 같이 못 둔다(규격 위반) |

⚠ **`211.236.39.251` 은 죽어 있다.** 80·443 둘 다 열려 있지 않다(실측). A 레코드가 세 개라
방문자는 셋 중 하나로 무작위 배정되므로 **지금도 대략 1/3 이 15초를 기다리다 실패한다.**
(같은 대역의 `211.236.39.250:3400` = 업무 포탈은 살아 있다. 이것과 헷갈리지 않는다.)

TXT `v=spf1 include:spf.protection.outlook.com -all` 과 `MS=ms42859694` 는 **메일(M365)** 이다.
홈페이지와 무관하니 **건드리지 않는다.** 지우면 회사 메일이 스팸으로 떨어진다.

### 4단계 — HTTPS

DNS 검사가 초록이 되면 저장소 Settings → Pages 에서 **Enforce HTTPS** 를 켠다.
인증서 발급은 전파 뒤 **몇 분~한 시간**이 걸리고, 그 사이 https 는 경고를 낸다.

### 바꾸기 전 상태 (2026-08-13 실측 · 되돌리기용)

```
acrofuture.com      A     185.199.108.153 / 211.236.39.251 / 185.199.109.153   TTL 3600
acrofuture.com      CNAME snake0207.github.io   (apex CNAME 평탄화)
www.acrofuture.com  CNAME snake0207.github.io
www.acrofuture.com  A     211.236.39.251 / 185.199.108.153 / 185.199.109.153
acrofuture.com      TXT   v=spf1 include:spf.protection.outlook.com -all
acrofuture.com      TXT   MS=ms42859694
```

## 임시 공개 터널과의 관계

`acro.stock-autotrade.com`(Cloudflare 터널 → localhost:3100)은 **이 PC 가 켜져 있어야만**
뜨는 검토용 통로다. Pages 로 옮기고 나면 역할이 겹치므로, 도메인 전환이 끝나면 끈다.
켜고 끄는 법은 메모리 `acrofuture-web-tunnel` 에 있다.

## 저장소에 없는 것

`research/`(회사 소개서 PDF·추출 이미지 53MB)는 **올리지 않았다.** 공개 저장소라
소개서 원문이 통째로 배포되는 것을 피했다.

- 빌드·배포에는 지장 없다 — 구워 놓은 `site/public/media` 는 저장소에 있다.
- ⚠ 캡처를 **다시 구우려면**(`scripts/build-media.mjs`) 원본이 있는 이 PC 에서 해야 한다.
  다른 PC 에서 필요하면 `research/` 를 따로 복사해 온다.
